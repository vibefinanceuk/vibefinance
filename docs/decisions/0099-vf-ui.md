# 0099 — `vf-ui`, and the first screen

**Status: built, not deployed.** The Worker, the sign-in screen, and
configuration injected rather than compiled in.

---

## Its own Worker

Decision 0083 section 4 settled this on **deployment frequency**:
binding the UI to `vf-licence` means every UI change redeploys the
component that mints licence tokens for the entire fleet, and UI changes
are far more frequent than control-plane changes.

The Worker itself does almost nothing. Cloudflare serves static files
before it runs; this exists to inject configuration and to answer paths
no file matches.

---

## The API address is configuration

`LICENCE_API` is a var, served to the page as `/config.js`.

**If it were compiled into the JavaScript, moving to a custom domain
would mean rebuilding the UI.** As a var it is a deployment setting, and
both origins can be served during a transition — which matters, because
a custom domain is expected later.

A `<script src>` rather than JSON fetched at startup, so the value is
present before any code needs it. Same reasoning as serving branding as
CSS: a thing needed for the first paint should not require a round trip
after it.

`JSON.stringify` rather than concatenation. The value comes from
deployment configuration rather than a user, but a URL interpolated raw
into JavaScript is a shape of mistake worth not making at all. A test
asserts the output parses.

---

## Two stages, because the selector cannot come first

The environment list cannot be shown until somebody has proved who they
are — decision 0083 section 5: the selector **lists what you can reach,
not what the customer owns**, and answering that unauthenticated would
turn an email address into a map of a customer's estate.

So: `POST /my-environments` when the person leaves the password field,
then `POST /login` with the chosen environment.

**The password is sent twice**, deliberately rather than unfortunately.
The alternative is a first-stage token — a second credential type to
design, scope and expire, for the sake of one round trip.

---

## Branding as a stylesheet, applied over the structural tokens

Two `<link>` elements: `tokens.css` shipped with the UI, then the
customer's livery fetched from `vf-licence` (decision 0096).

Both apply **before the first paint**. Fetching branding as JSON and
setting variables in script would mean a visible flash of the wrong
colours.

The structural tokens are the fallback — what somebody sees before a
customer is known, and what a customer with no livery keeps.

---

## The session is held in memory, and that is not a decision

**It does not survive a refresh.**

- `sessionStorage` survives and is readable by any injected script.
- A cookie survives and introduces a second authentication mechanism
  alongside the bearer token, which decision 0083 was pleased to avoid.

In memory is the option that **defers the choice without pretending it
has been made**. Recorded as open rather than settled quietly, because
the first person to refresh the page will ask.

---

## What a person is told after signing in

The last sign-in and every failed attempt since — what ISO 27001:2022
Annex A 8.5 asks for, and the reason attempts are kept after a success
rather than cleared (decision 0090).

Rendered with `textContent`, never `innerHTML`. **A source address is
exactly the field somebody would try to put a script tag in**, and it
arrives from an API into a page.

---

## What is not built

- **No screen after signing in.** The token is obtained and there is
  nowhere to go. The Validation queue is the next piece, and it needs
  `vf-app` routes accepting sessions — only `/whoami` does.
- **`ALLOWED_ORIGINS` is unset** on both API Workers, so a browser
  cannot yet read either response (decision 0098). It needs this
  Worker's origin, which needs it deployed.
- **No custom domain.** `vf-ui.vibefinance.workers.dev` to start; adding
  one later is a routing change plus two config values.
- **No sign-out**, because there is no persisted session to clear.
